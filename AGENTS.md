# AGENTS.md

## Stack
Next.js 16 App Router + React 19 + TypeScript (strict) + Tailwind CSS v4 + Supabase (Auth + Postgres) + Telegram Bot API. No tests, no CI, no test framework — don't add tests unless asked.

UI is Arabic and RTL: `lang="ar" dir="rtl"` in `app/layout.tsx`, and every user-facing string (page copy, button labels, `{ error: "..." }` returns) is in Arabic. New UI strings should be Arabic.

## Commands
- `npm run dev` — dev server on http://localhost:3000
- `npx tsc --noEmit` — typecheck (no npm script exists; this is the reliable verification gate)
- `npm run build` — production build (verified working; needs valid Supabase env). No `next.config.mjs` exists in this repo. Fonts are `next/font/google` (Readex_Pro, Rubik, JetBrains_Mono) in `app/layout.tsx` — fetched at build time, so a build with no network fails.
- `npm run start` — self-hosted `next start` only; the in-process scheduler ticker (`ensureSchedulerTicker`) starts only here (not under `npm run dev`), and only when `TELEX_SERVICE_ROLE_KEY` is set.
- `npm run lint` — **currently fails**: `eslint.config.mjs` actually exports a Next config object (`export default nextConfig` with `eslint.ignoreDuringBuilds`), which ESLint 9 rejects with `ConfigError: Unexpected key "eslint"`. There is no `next.config.mjs`, so the `ignoreDuringBuilds` setting effectively lives in the wrong file and does nothing. If you touch this, the config object belongs in a real `next.config.mjs` and `eslint.config.mjs` needs a valid flat config. Don't treat lint as part of your verification pass.

Known quirk: `eslint-config-next@15` is installed alongside `next@16` (version mismatch is intentional/current; don't "fix" it).

## Env & Supabase
- Five env vars in `.env.example` (copy → `.env.local`): `TELEX_PUBLIC_SUPABASE_URL`, `TELEX_PUBLIC_SUPABASE_ANON_KEY` (browser-exposed; read in `lib/supabase/server.ts` and `lib/supabase/client.ts`), plus server-only `TELEX_SERVICE_ROLE_KEY`, `TELEX_CRON_SECRET`, and `TELEX_ENCRYPTION_KEY` (any string; derives the AES-256 key for secrets at rest via SHA-256). Browser-facing vars use the `REBEX_PUBLIC_` prefix; new server-only vars use plain `REBEX_`. The bot token lives at runtime in the `telegram_bot` singleton DB row — **encrypted at rest** by `lib/crypto.ts` (AES-256-GCM, stored as `enc:v1:<iv>:<tag>:<ct>`; `decryptSecret` passes values without that prefix through untouched, so legacy plaintext rows keep working with no migration). Set through the Settings "Connect bot" action, never in env. Rollout: after setting `TELEX_ENCRYPTION_KEY`, re-save the bot token, watch bot, and webhook in Settings/Commands to re-encrypt old values (encryption is fail-closed: no key → connect/send throw a clear Arabic error).
- The auth guard is `requireAdmin(supabase)` from `lib/supabase/admin.ts` (NOT a bare `supabase.auth.getUser()` check): it validates the session, `admin_config.admin_id`, **and MFA** (see Security). Every server action and the in-app `/api/*` routes (`/api/groups`, `/api/topics`) use it; actions return `{ error: ADMIN_ERROR }`, API routes return 403. Don't remove those guards. `requireAdminForPage()` is the same decision with a `reason` (`unauthenticated` / `not_admin` / `mfa_required`) so `app/dashboard/layout.tsx` can route an admin who still owes a TOTP code to `/login?step=mfa` instead of a pointless `/login` bounce. `lib/supabase/server.ts` throws a descriptive error if the public Supabase env is missing.
- Schema lives in `supabase/migrations/` as a **four-file baseline** — `01_core.sql` (bot, chats, topics, admin identity, commands, templates, `is_admin()`, all RLS), `02_bot_features.sql` (`scheduled_messages`), `03_audit.sql` (`audit_logs` + retention), `04_login_limiter.sql` (`login_attempts`) — applied manually in the Supabase SQL editor, **all four in order**. There is no migration runner. Each file is a single `begin`/`commit` transaction, so a failure rolls back the whole file rather than leaving half a schema. Two further files, `05_drop_dead_functions.sql` and `06_lock_down_rpc_grants.sql`, are forward migrations for databases that predate the baseline and are no-ops on a fresh setup;
- **The four baseline files are immutable.** Do not change the schema by editing them — once a real database stands up from them, editing silently forks it from the next one with nothing to detect it. Add `05_*.sql`, `06_*.sql` after them instead. Every baseline statement is replay-safe (`create table/index if not exists`, `create or replace function`, and each `create policy` immediately preceded by its own `drop policy if exists` — the only `drop` in the baseline, and what makes a policy re-creatable).
- Since Oct 30, 2026 the Data API no longer auto-grants on new public tables, so **any file that creates a table must include `grant all on table public.<t> to anon, authenticated, service_role;`** (all ten baseline tables carry it). RLS is what actually restricts access; the grant only keeps the table reachable. Postgres rejects `NOT NULL` on a function parameter, and rejects a non-defaulted parameter that follows a defaulted one — so put required parameters first (see `insert_audit_log`); callers use named arguments, so the order stays invisible to them. The `revoke`/`grant` signature string must match the declared order exactly, or it targets a function that doesn't exist — and note `REVOKE … ON FUNCTION` **errors** if the function was never created, which is why the baseline carries no revoke for the three dead functions the archive created; `05_drop_dead_functions.sql` drops them from existing databases instead.
- Verifying a fresh setup against an existing database: `scripts/schema-dump.sql` is a read-only query that emits RLS flags, columns, **policy predicate bodies**, indexes, constraints, function security attributes, and the three Data API roles' privileges, one sorted text column. Run it in both projects and diff — the policy predicates are invisible through PostgREST, and a wrong one fails silently. It is the only way to compare schemas here: there is no `psql`, no `supabase` CLI, and no DB password in the env, so `supabase db diff` is not available.
- Tables: `telegram_bot` (singleton via `singleton` boolean; main `bot_token`/`bot_id`/`bot_username` + optional `watch_bot_token`/`watch_bot_id`/`watch_bot_username` for topic discovery), `telegram_chats` (`telegram_chat_id` unique, `is_forum`), `telegram_topics` (chat-id + `message_thread_id` unique pair, nullable `name` — a *learned cache*, plus `is_manually_named` so manual renames survive refreshes), `admin_last_login` (singleton; latest login upserted in `app/login/actions.ts`, shown in the sidebar), `admin_config` (singleton row holding the authoritative `admin_id`, seeded from `auth.users` by `01_core.sql`), `telegram_commands`, `message_templates`, `scheduled_messages`, `audit_logs` (`03_audit.sql`; append-only trail, hashed IP/UA, admin-read via `is_admin()`, written only through the SECURITY DEFINER `insert_audit_log`), `login_attempts` (`04_login_limiter.sql`; hashed email/IP ledger behind the DB-backed sign-in limiter, RLS on with no policies so only `service_role` touches rows). RLS is admin-only via the SECURITY DEFINER `is_admin()` helper (`01_core.sql`) — it does not trust "any authenticated user".
- Auth: one admin user is created in the Supabase console; `admin_config.admin_id` must point at their UUID (`01_core.sql` seeds it from the last/first login — a no-op on a project with no users yet, so if it's blank, insert the UUID manually). TOTP factors live in Supabase's own `auth.mfa_factors` — never create or read that table from app code except in the documented emergency recovery. `app/dashboard/layout.tsx` guards with `requireAdminForPage`. Root `/` is the public Arabic landing page (`components/landing/*`): it always renders, and a single `getUser()` call only swaps the header/hero CTA between `تسجيل الدخول` → `/login` and `لوحة التحكم` → `/dashboard`. Nothing else on that page depends on the session, so the call is for the CTA alone. It is the only indexable route — `public/robots.txt` disallows `/dashboard`, `/login`, `/api`; `app/sitemap.ts` lists `/` alone, and `metadataBase` in `app/layout.tsx` is the hardcoded public domain.

## Architecture
- Supabase server client `createClient()` in `lib/supabase/server.ts` is `async` — must `await` it. `lib/supabase/client.ts` (browser client) may only be imported from `"use client"` components. There is also a service-role client, `createServiceClient()` in `lib/supabase/service.ts` (module-cached, requires `TELEX_SERVICE_ROLE_KEY`) — used by the scheduler, the webhook route, and the audit trail (`lib/audit.ts`), never for ordinary page data. `createTransientAuthClient()` (same file) is an un-cached, `persistSession: false` client on the **anon** key, used only to prove a password in `changePassword` without rewriting the caller's session cookie; `createServiceClient()` must never be used to sign in (it would leave a live admin-capable refresh token in a shared, module-cached client).
- Server actions live under `app/<route>/actions.ts` with `"use server"` and are imported directly into client components. Pattern: `requireAdmin` (plus `rateLimit` on send/refresh), call the Telegram API to validate, then Supabase `upsert` with `onConflict`, then `revalidatePath` the affected routes. They return `{ ok }` or `{ error: msg }` — no exceptions to the component.
- `lib/rate-limit.ts` is an in-memory per-process bucket map (login per-email + per-IP, MFA codes, send, topic-refresh, cron per-IP, webhook per-IP, command buckets by user/chat/bot via `rateLimitOnce`) — no shared store, so limits reset on every instance/restart. Best-effort; never a hard security boundary across instances. Sign-in is the one place where it is only the *first* line: `lib/login-limiter.ts` adds the durable, cross-instance `login_attempts` ledger behind it.
- Telegram wrapper is `lib/telegram/client.ts` (`getMe`, `getChat`, `sendMessage`, `getUpdates`, `setMyCommands`, `setWebhook`, `deleteWebhook`). Group chat IDs can't be enumerated via the Bot API, so adding a group validates the chat ID with `getChat`.
- Forum topics: the Bot API has **no method to enumerate topics**, so `telegram_topics` is a learned cache. Populated two ways: (a) auto-capture on send (`sendTelegramMessage` upserts chat+`message_thread_id` with a null name, unless `is_manually_named`), and (b) `refreshChatTopics` in `app/dashboard/groups/actions.ts`, which long-polls `getUpdates` and extracts thread ids from topic messages plus real names from `forum_topic_created`/`forum_topic_edited` events, then upserts on the `(telegram_chat_id, telegram_thread_id)` unique pair, skipping manually-named topics (`renameTopic` sets `is_manually_named`). The scan ACKs updates via `offset` — safe only while no webhook is in use on the scanned bot. Two-bot model (migration `012`): the webhook on the main bot blocks its `getUpdates`, so `refreshChatTopics` scans with `watch_bot_token ?? bot_token` — a second BotFather bot added to the same groups (never given a webhook) keeps topic refresh working while commands are connected; when the webhook is active and no watch bot is set, the refresh returns a guided Arabic error instead of a 409. Guards: `refreshChatTopics` treats `watch_bot_token === bot_token` as "no watch bot", calls `getWebhookInfo` on the scan bot (refusing to scan a bot that has a webhook registered), translates any `Conflict … webhook is active` (409) error into Arabic, and returns a `scannedWith` username so the Groups page shows which bot did the refresh. Settings refuse the same token in both directions (`connectBot` vs `connectWatchBot`) and refuse a watch bot that already has a webhook. `message_thread_id`s are chat-scoped, so the main bot can send into topics discovered by the watch bot (both bots just need to be group members). The send composer shows "General" (no `message_thread_id`) or stored topics; topic management lives in the Groups page.
- Scheduled messages (`/dashboard/schedule`): `scheduled_messages` rows drive sends; each row has a `title` (default `جدولة جديدة`, from `SCHEDULE_DEFAULT_TITLE` in `lib/types.ts`) shown in the list and editable on add/edit; nothing fires them except `runDueScheduled()` in `lib/scheduler/run.ts`. It's triggered by (a) `app/api/cron/route.ts` (GET/POST guarded by `x-cron-secret` against `TELEX_CRON_SECRET`) and (b) an in-process 60s ticker, `ensureSchedulerTicker()`, which only starts on self-hosted `next start` when `TELEX_SERVICE_ROLE_KEY` is set (invoked from `app/dashboard/layout.tsx` and `/api/cron`). Concurrency safety is by per-row optimistic claim — no advisory lock (the RPCs exist in migration 008 but are unused; session-level `pg_try_advisory_lock`/`pg_advisory_unlock` are ineffective across Supabase's pooled PostgREST connections, which used to double-send). `runDueScheduled()` selects due rows, then "claims" each one with a conditional UPDATE that sets `next_run_at` to a 5-minute sentinel and only matches the row's currently-selected `next_run_at`; exactly one of the concurrent runners wins the UPDATE (`select("id").length === 1`) and the loser skips it, so each message is sent once even when the cron pinger and the in-process ticker race. A crash between claim and finalize self-heals when the sentinel expires. Failures retry with backoff (`lib/scheduler/schedule.ts`) up to `MAX_CONSECUTIVE_FAILURES` (5), then the row is marked `failed`. README has the pg_cron `net.http_post` → `/api/cron` setup (needs `pg_cron` + `pg_net` extensions) for serverless deploys.
- The send composer is a `contenteditable` + `document.execCommand` editor. `lib/telegram/format.ts` (`editorHtmlToTelegramHtml`) converts its HTML to a strict allowlist of Telegram-safe tags via `DOMParser` — browser-only code, the single source of truth for `parse_mode: "HTML"`. Spoilers: the toolbar button calls `toggleSpoiler` in `lib/telegram/spoiler.ts`, which wraps the selection in a `span.spoiler` (or unwraps one); the converter emits it as Telegram's `<tg-spoiler>` tag. Inline code and highlight wrap the selection manually too (`toggleCode`/`toggleMark` in the same file) because Chrome's `execCommand("formatBlock", "CODE")` is a no-op (formatBlock only accepts block tags) and `<mark>` needs to stay wrappable. The same editor/helper is used in the command, template, and schedule editors.
- `@/*` path alias maps to repo root (`tsconfig.json`). Tailwind v4: `@import "tailwindcss"` + `@theme` tokens in `app/globals.css`, wired via `@tailwindcss/postcss` in `postcss.config.mjs` — no `tailwind.config` file.
- Theme is custom, no `next-themes`. `components/theme-provider.tsx` (client) holds a `ThemeProvider` + `useTheme` hook toggling the `dark` class on `<html>` and persisting to `localStorage["theme"]`; it listens to `prefers-color-scheme` when nothing is stored. `app/layout.tsx` has an inline `<script>` in `<head>` that applies `dark` from storage or system preference before first paint (prevents FOUC). Sidebar imports `useTheme` from `@/components/theme-provider`.
- `components/brand-mark.tsx` (`BrandMark` + `BrandLockup`) is the single product mark, used by the dashboard sidebar, `/login`, and `app/not-found.tsx`. `size` is the square edge in px and `radius` is an explicit prop — **do not** try to override the radius via `className`, because two conflicting Tailwind utilities resolve by CSS source order, not attribute order, so it silently does nothing.
- Bot commands ("Boot command"): `telegram_commands` table (single row per `command` unique) with a `response` (Telegram-safe HTML, what the bot actually sends), `is_rich` (whether `response` is rich-HTML sent via `sendRichMessage`), and `editor_html` (raw WYSIWYG source for re-editing). `app/dashboard/commands/actions.ts` does CRUD + `toggleCommand`, syncs the enabled list to Telegram via `setMyCommands`, and persists `is_rich`. The bot receives commands via a webhook at `app/api/telegram/webhook/route.ts`; connecting it stores a random `webhook_secret` on the `telegram_bot` row and calls `setWebhook` (URL + `secret_token`). The webhook route is unauthenticated by design: it authorizes via the `X-Telegram-Bot-Api-Secret-Token` header (timing-safe compare against the stored secret) and rate-limits — per IP (60/min) plus command buckets per Telegram user (10/min), per chat (30/min), and bot-wide (150/min) via `rateLimitOnce`; a limited bucket sends exactly one Arabic slow-down notice per window, then commands are silently dropped (200 OK, no Telegram retry). It then replies through the service-role client — it does NOT use the `bot_command_response` RPC (grants revoked in migration `007`), and branches on `is_rich` to call `sendRichMessage` (`rich_message: { html, is_rtl: true }`) instead of classic `parse_mode:"HTML"`. HTML→Telegram conversion happens client-side at save time (shared `telegramSavePayload` in `lib/telegram/format.ts`), so the server never parses HTML. Caveat: an active webhook blocks `getUpdates`, so `refreshChatTopics` (long-polling) fails while connected — unless a watch bot (migration `012`) is configured, in which case the refresh scans with the watch bot's token instead and both features work at the same time. Reflected in the Commands page note and the Settings "بوت مراقبة المواضيع" section.
- Message templates: `message_templates` table (`title` + `response` Telegram-safe HTML + `editor_html` raw source, mirroring `telegram_commands`). The send composer (`components/send-composer.tsx`) can load an existing template into the editor via a dropdown and save the current draft as a template (prompted for a title); `/dashboard/templates` (`app/dashboard/templates/actions.ts` CRUD + `components/templates-manager.tsx` WYSIWYG form/manager) handles full management. All template routes revalidate `/dashboard/templates` and `/dashboard/send`.

## Security
- **Headers + CSP**: `proxy.ts` adds `Content-Security-Policy` with a per-request nonce (`script-src 'self' 'nonce-…' 'strict-dynamic'`; dev adds `'unsafe-eval'`), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY` + `frame-ancestors 'none'`, `Permissions-Policy` (camera/mic/geo off), `Cross-Origin-Opener-Policy`/`Cross-Origin-Resource-Policy: same-origin`, HSTS when https, and `Cache-Control: no-store` on `/api/*`. Next.js applies the nonce to its own inline scripts automatically from the `x-nonce` request header; the theme FOUC script in `app/layout.tsx` reads the same nonce via `headers()` and sets it on its `<script nonce>`. Only the toolbar/menu inline style attributes and the two inline scripts (theme + Next bootstrap) need allowances — keep it that way; don't add `'unsafe-inline'`/`'unsafe-eval'` to production CSP. Proxy replaced the deprecated `middleware.ts` convention in Next 16 (codemod: `npx @next/codemod@canary middleware-to-proxy .`); it always runs on the **Node.js** runtime, so `node:crypto`/`Buffer` are available and a route segment `runtime` export there is a build error. The two files are mutually exclusive — having both fails the build.
- **Session cookies**: `lib/supabase/server.ts` forces `httpOnly: true`, `sameSite: "lax"`, `secure: isProd`, `path: "/"` on the Supabase auth cookie (the `@supabase/ssr` default is `httpOnly: false`), so the session token is not readable by JS and not sent cross-site. All auth is server-side — the browser client in `lib/supabase/client.ts` is currently unused.
- **Login**: `app/login/actions.ts` rate-limits per email (10/min) AND per IP (30/min), normalizes email (trim/lowercase), and returns a generic Arabic error ("بيانات الدخول غير صحيحة.") — never reveals whether the email exists or leaks raw Supabase errors. On top of the in-memory buckets it consults the durable limiter in `lib/login-limiter.ts` (migration 014): 5 **failed** attempts per `(email_hash, ip_hash)` pair per 15 minutes, counted by the SECURITY DEFINER `count_login_attempts`. Pair keying is deliberate (a per-email-only cap would let anyone lock the admin out from a throwaway IP); a request with no IP header narrows the key to the email instead of removing the limit, and rows with a null `ip_hash` are never counted against an IP-bearing request (otherwise no-IP requests could inflate every IP's counter). **The limiter fails OPEN** — a missing migration, bad RPC, or DB outage returns "not blocked" and records `app.login_limiter.error`, because locking the single admin out of their own dashboard is worse than one extra guess. All attempts are recorded in `login_attempts` (emails/IPs as SHA-256 hex, never raw) and every outcome is audited.
- **MFA (TOTP)**: enrollment + password change live at `/dashboard/security` (`app/dashboard/security/actions.ts` + `components/security-manager.tsx`, sidebar link "الأمان"). Supabase's own `auth.mfa` API manages the factors — never a local table. Sign-in is two-step: `login()` (password) keeps the aal1 session and redirects to `/login?step=mfa`, then `submitMfa()` verifies the code with `mfa.challengeAndVerify`, which promotes the session to aal2 (and revokes the admin's other sessions). Enrollment is `mfa.enroll` (returns QR data-URL + base32 secret + otpauth URI, shown once, never logged) followed by `verifyMfaEnrollment`; unverified factors left by an abandoned attempt are dropped first so retries can't hit `mfa_factor_name_conflict` / `too_many_enrolled_mfa_factors`. **Read factors from `listFactors().data.all`, never from the per-type buckets** — auth-js only pushes into `data.totp`/`data.phone`/etc. when `status === 'verified'`, so an unverified (just-enrolled) factor is invisible there and `verifyMfaEnrollment` would never find the pending factor. `listAllFactors` in `lib/supabase/mfa.ts` is the only reader of `all`; `listVerified/UnverifiedTotpFactors` filter it by hand. The security page also lists every factor (all types, verified or not) with a per-factor delete (`deleteMfaFactor`, aal2 required only for a verified one, id resolved from the admin's own list so it can't name a foreign factor) — that's the escape hatch for a half-finished enrollment. `requireAdmin` enforces it and **fails closed**: once a verified factor exists, an aal1 session is rejected exactly like an anonymous one, so MFA cannot be skipped by hitting `/dashboard` or an action directly; `lib/supabase/mfa.ts` (`readMfaState`/`mfaSatisfied`) is the only place that decides, and an unreadable MFA state denies. The AAL claim is read from the session JWT (free), and only an aal1 session pays the extra `listFactors()` round trip, because the session's cached user object can predate the enrollment. `unenrollMfa` additionally demands an aal2 session (GoTrue requires it anyway; checking first yields a clear Arabic message). `changePassword` proves the current password on `createTransientAuthClient()` — never on the cookie client, which would overwrite the aal2 cookie with a fresh aal1 one and lock the admin out — then updates the password and calls `signOut({ scope: "others" })`. Supabase Free has no recovery codes, so **the QR/secret backup taken during enrollment is the only recovery path** (README "استعادة الدخول").
- **Audit trail**: `lib/audit.ts` `logAudit(event, meta, { source, actorId })` writes through the SECURITY DEFINER `insert_audit_log` using the service-role client (sanctioned call site — a failed sign-in has no session to write with). It is best-effort and **never throws**; a non-whitelisted event prefix is dropped with a console warning (mirrored by the SQL CHECK constraint). `insert_audit_log` and `count_login_attempts` are granted execute to `service_role` **only** — never to `anon` or `authenticated`, or the browser could forge audit rows / probe the limiter as an account-enumeration oracle; the tables themselves still need the `grant all ... to anon, authenticated, service_role` block for the Data API. **When adding a SECURITY DEFINER function, revoke from `anon, authenticated` by name, not just from `public`** — see the grant-idiom warning below. No PII: `meta` carries booleans/enums/counts, and IPs/user agents are SHA-256 hashed by `lib/hash.ts` before they leave the module. Events are `auth.*` (signin blocked/failed/success/challenge, `mfa.*`, `password.*`), `app.login_limiter.error`, `settings.bot.*` / `settings.watch_bot.*`, and `admin.*` (webhook connect/disconnect, command/template/group/topic/schedule deletions). Retention: migration 015's `purge_audit_logs_older_than(30)` is called best-effort from the dashboard layout via `maybePurgeAuditLogs()` (in-process rate limit of one attempt per hour, fire-and-forget) — no cron needed.
- **Secrets at rest**: `lib/crypto.ts` encrypts `bot_token`/`watch_bot_token`/`webhook_secret` with AES-256-GCM keyed by `TELEX_ENCRYPTION_KEY` (stored as `enc:v1:<iv>:<tag>:<ct>`). Encrypt on write (Settings connect, Commands connect webhook), decrypt on every Telegram API use and before any same-token comparison (e.g. the watch-bot equality checks in `refreshChatTopics` — encrypted ciphertexts differ per write, so compares MUST be on decrypted values). Webhook route fails closed: a stored secret that can't be decrypted → 403 (not 500), so Telegram doesn't retry-storm. Legacy plaintext passes through, enabling a no-migration rollout.
- **Grant idiom — `revoke … from public` is not a lockdown.** Every SECURITY DEFINER function here was originally locked with `revoke all on function X from public; grant execute on function X to service_role;`. That does not work on Supabase: the platform applies `ALTER DEFAULT PRIVILEGES` granting EXECUTE on new `public`-schema functions to `anon` and `authenticated` **by name**, and `REVOKE … FROM public` only removes the PUBLIC-derived grant, leaving those explicit per-role grants intact. Measured on production with only the public anon key: `insert_audit_log` wrote a row, `purge_audit_logs_older_than` and `count_login_attempts` answered, and `bot_command_response` answered — including a function `007`'s comment claims it revoked. RLS itself was verified intact (anon read 0 rows from all six RLS-enabled tables), so this is a function-grant defect, not an open database. **Always `revoke … from public, anon, authenticated` and then grant explicitly.** The baseline does this, so fresh setups are correct; `06_lock_down_rpc_grants.sql` fixes the live one. Corollary for testing: PostgREST returns `PGRST202` both for "no such function" and for "argument names did not match", so a probe guessing `p_key` against a function taking `key` wrongly concludes it is absent — confirm with `has_function_privilege` (already in `scripts/schema-dump.sql`).
- **Brute-force surfaces**: `/api/cron` rate-limits per IP (10/min) before the timing-safe `x-cron-secret` check; the webhook route rate-limits per IP and per command buckets (`rateLimitOnce`, warn-once Arabic notice). Note `admin_config.admin_id` + `requireAdmin` is the only authorization boundary — never weaken it.
- **Unfixed on production** (needs a Settings round-trip or `05`/`06`, neither is app code): `bot_token` and `watch_bot_token` are stored **plaintext**, since `REBEX_ENCRYPTION_KEY` was introduced after those rows were written. `decryptSecret` passes them through, so the app works; re-save both in Settings to get `enc:v1:` rows. Relatedly `webhook_secret` is currently `NULL`, which is the only reason `bot_command_response` returns `[]` rather than the bot token — `05_drop_dead_functions.sql` removes that function instead of relying on that.
- **XSS posture**: single admin with server-rendered React (auto-escaped) + CSP nonce; stored message HTML is converted client-side to a Telegram-safe allowlist (`lib/telegram/format.ts`) and Telegram sanitizes what the bot sends. Never render raw stored editor HTML with `dangerouslySetInnerHTML` outside the editor itself.
- **Focus ring**: one global rule in `app/globals.css` covers `button, input, textarea, select, a` in **both** the `outline: none` list and the `:focus-visible` ring list. `a` is in both on purpose — links used to fall through to the browser's default ring, so the app showed two different focus indicators. If you add a selector to one list, add it to the other or that element ends up with both rings.
- **Contrast floor**: `--success`, `--danger` and `--muted` all clear WCAG AA 4.5:1 against `--background` in **both** themes. `--success` is a real green (emerald `#047857` light / `#34d399` dark), deliberately **not** the accent blue: blue made a "تم الحفظ" confirmation look like a link, and it failed AA in dark mode (3.66:1) because `.dark` never overrode it. Re-check any change to these values with a contrast tool.
